# What the observer must do to use the field map

The production observer (`superbuilders/aeo alpha-site-system`) today compares the site with sources and reports "site says A, source says B". To file tickets that a fresh agent can execute, it needs the pathway logic from `spec/campus-page-field-map.json`. Required changes, in order:

1. **Read HubSpot Programs directly.** Set `HUBSPOT_PROGRAMS_ENDPOINT` (it has no default today, so every campus-fact check is inert) with a token that has `crm.objects.custom.read` and `crm.schemas.custom.read`. The production observer requests `website_campus_intro` together with the governing Program properties. Add any still-missing fields such as `cognia_accredited`, `form_program_interest_label`, `wordpress_post_id`, and `visibility` before enforcing checks that depend on them. The growth map API stays the fallback for state and mirrored facts.
2. **Status-sentence checks (implemented 2026-09-25).** `campus-source-status-sentence` compares `website_campus_intro` with HubSpot Program `type`; `campus-page-status-sentence` compares the rendered page with the source-approved lifecycle sentence. For every Open Program, both must contain "<name> is open and enrolling."; for Announced, both must carry a month or season plus a year. A source contradiction routes to `hubspot-data`; a correct source that failed to reach the page routes to `sync-delivery`.
3. **Classify by pathway before dispatch.** For each failing check, resolve the element in the field map and emit the defect class (data, mapping, delivery, presentation) and the ticket class. Route `hubspot-data` to the hubspot-program-admin, `sync-mapping` and `sync-delivery` to the n8n-sync-owner, event classes to the events-plugin-owner and hubspot-owner, and only presentation classes to the website operators. Today every campus rule routes to `#support-websites` with Matt and Yash as owners.
4. **File with the template.** The APEX ticket body carries the element, CSS ID, source system and field, source value with read time, expected value and rule, class, owner, fix path, and done condition (protocol step 1b templates). `tests/diagnose-field.mjs` is the reference implementation; the observer can call it or port it.
5. **Know the run schedule.** Treat a page modified at 00:15 to 01:00 Central as rewritten by n8n. A mismatch after that window with a correct source is `sync-delivery`, not a website defect. Replace the unexplained 2-hour grace constant for events with the plugin's 30-minute interval plus one cycle.
6. **Check synced elements exist.** Port `n8n-synced-elements-present` from `tests/page-check.mjs` so a layout change that drops a CSS ID is caught before the nightly run fails.

Until 1 to 4 land, the loop's campus-fact and launch-copy findings are triaged by an agent running `tests/diagnose-field.mjs` before any ticket is worked.

## Added 2026-09-24: the check bundle is the definition

## Added 2026-09-25: promotion rule, depth, source digest, filer trigger (check bundle 1.2)

- **Promotion rule.** A row is enforced only when its `grounding` names a complaint, a source contract, an exemplar or a decision (the 2026-09-15 precedence, in that order of authority: decision, source-of-truth system, exemplar, complaint). A row whose grounding is `none` is built as `status: advisory` with `advisoryReason` set, whatever `spec/check-rows.json` declares: the observer measures it and reports it, the filer never files it. Promoting a row means grounding it (a decisions.md row, a spec or registry contract, an exemplar URL, or the ticket or findings document that complained) and rebuilding; nobody edits `status` on an ungrounded row.
- **Depth.** Every row carries `depth: render | http` (`spec/README.md`, "Depth contract"). Render campus pages, the homepage, Locations and the events pages (and the `map-routes` and `critical-routes` groups) in the browser on both viewports; fetch every other route over HTTP once; read `map-source` rows from the sources with no fetch. Never take a rendered measurement on an `http` row; the builder refuses such a row and a finding that claims one is telemetry.
- **Source digest.** Rows with `channel: source-digest` (the `map-source` comparisons between the Operations sheet, the growth map API and HubSpot Programs, and the Community record, URL form and host rows) are emitted like any other finding, with `expectedSource`, `actualSource` and `sourceReadAt` filled, because the filer turns each into an audit line for the owner role in `source-digest.md`; they never become website tickets and the observer never dispatches them anywhere itself.
- **Filer trigger.** When `site-observe.yml` completes with conclusion success, send `repository_dispatch` `observer-run-completed` to `trilogy-group/alpha-website-playbook` with `client_payload.run_id` (this GitHub run id), `client_payload.mode` (`full` or `events`) and `client_payload.conclusion`; the playbook's filer workflow is a receiver for that event (cross-repository `workflow_run` is not supported) and files after each full run, with a fallback cron at 06:45 and 21:45 UTC. The token needs `repo` dispatch rights on the playbook repository. Until the dispatch step lands in aeo, the fallback cron carries the cadence.
- **Cadence.** Full render runs at 06:00 and 21:00 UTC; events lane every two hours; source contracts daily at 06:30 UTC; loop-health rows every run. `clearAfterRuns: 2` means two consecutive full runs, about one day.

## Added 2026-09-25: presence not absence, source-first enumeration (check bundle 1.3)

Decision by Matt Barge, 2026-09-25 (Slack): "not only go from viewing the website and then checking HubSpot, but go from HubSpot to checking the website." The bundle carries it as data; the observer implements exactly these fields (`spec/schemas/check-bundle.schema.json`):

- **`entitySource`** on every row (`hubspot-programs` | `map`, default `map`; the bundle's `entitySources` block names each source's fields). For `hubspot-programs` rows, enumerate the HubSpot Programs whose `type` is one of `publicTypes` and whose `website` host is one of `publicHosts`; take the lifecycle state from `type`; fetch the page at `website` with the trailing slash normalised. The map and the WordPress page list never decide which campuses exist.
- **`expected.derive.onMissing`** (`finding` | `skip`, default `skip`). On `finding`, an in-scope entity with no entry in the registry named by `expected.derive.field` is emitted as a finding of the same row with `missingExpectation: true` (a null `openMedia` row is missing too); the filer titles it "no approved <literals.missingThing> recorded for <state> campus <name>" and files it Missing Info to the row's owner role with `literals.missingAsk`. A row's `literals` are published at `row.literals` and mirrored at `expected.literal` next to the derive, which is where `rules.literalValue` reads them. **`equals-approved-media`** is literal: the rendered slot's attachment id (the `wp-image-<id>` class or the widget's media id) equals the registry `attachmentId`, `openMedia: video` accepts the approved video widget, and a mismatch names the observed asset. `literals.launchWords` is the word list for the vision pass over the intro card and hero screenshot on full runs (repair 2); `literals.assetPatterns` stays as the deterministic backstop.
- **Coverage rows.** `campus-registry-coverage` (`site.coverage.open-campus-registries`): for each enumerated campus and each entry of `literals.registries` whose `requiredWhen.type` includes the campus type, emit one finding per missing registry entry with `missingExpectation: true`, `registry` (the registry name), `expected: { file, keyPath }`, `ownerRole` and the entry's ask; an entry with an empty `requiredWhen.type` is informational. `program-page-present` (`site.coverage.program-page`): every enumerated Program's page answers 200 after redirects, its title or H1 names the campus, and the map lists a record with that url; a missing or wrong page is the finding (critical), a page that is right but absent from the map is emitted with `actual.missingFromMap: true` (the filer writes it under `hubspot-map-sync` in the source digest). `campus-page-rendered` (`site.coverage.open-campus-rendered`, loop health): one finding per full run listing every Open campus page that was not rendered (`actual: [{ id, name, url }]`, `expected` the count of Open pages, `observed` the count rendered), so a run that renders nothing still says so.
- **Comparators.** `spec/observer-comparators.json` is a verbatim copy of the observer's `spec/supported-comparators.json` (35 types, aeo #37); the builder refuses a row outside it and the observer fails loop health on a bundle outside its own list, so add a type in the observer first.
- **Ids.** Cite the row id on every finding as before; `aliases.pageCheck` in the bundle is for the playbook's own found-ticket filer and needs nothing from the observer.


## Added 2026-09-25: bundle-versus-observer conformance (repair 3)

`campus.intro.media.current` said `equals-approved-media` while the observer counted stale launch words, and nothing compared the two; East Bay's launch card went unseen for 32 days (`docs/qc-loop-repair-plan-2026-09-25.md`, repair 3). The contract now runs from both ends, and each end fails closed.

**What the observer must publish (superbuilders/aeo `alpha-site-system`).**

- `spec/supported-comparators.json`: every comparator type the code implements, one line of semantics each. The playbook's `spec/observer-comparators.json` is a verbatim copy; add a type there first.
- `IMPLEMENTED_CHECKS` (`src/checks.mjs`): the set of every check id the code emits, kept equal to the ids the source calls by a test (`tests/conformance.test.mjs`), so the set cannot drift from the code. `registry/observer-checks.json` is the playbook's captured copy.
- `src/conformance.mjs` and `node alpha-site-system/src/cli.mjs conformance --bundle <path or url>`: for the loaded bundle, (a) every row `comparator.type` is supported; (b) every row `observerCheck` is implemented; (c) every row `entitySource` is one the observer enumerates (`map`, `hubspot-programs`); (d) every row with `expected.derive.onMissing: finding` names a registry file the observer loads and reads with `rules.fileValue` (the coverage row's `literals.registries[].file` included); (e) the literals the code reads are present where required (`launchWords` and `assetPatterns` on `campus-page-stale-launch-media`, `registries` on `campus-registry-coverage`, `rules` on `campus-expired-seasonal-cta`, `missingThing` and `missingAsk` on every onMissing-finding row); (f) every row channel is one the observer routes. Any failure is a non-zero exit and a report naming the row; an implemented check with no row is a warning (telemetry only).
- Every observer run records the assessment in the packet manifest as `conformance: { ok, failures[] }`, degrades loop health on a failure, and files the loop-health check `bundle-conformance` (row `site.loop.health.conformance`, check bundle 1.4) listing every failure; `comparator-unsupported` (row `site.loop.health.comparator-unsupported`) still names each unsupported type on its own.
- Semantic fixtures (`tests/conformance.test.mjs`, `tests/fixtures/conformance/`): for `campus.intro.media.current` (`equals-approved-media`), `campus.resources.booking.present` (`present`) and `site.seasonal.window` (`absent-after-date`), a fixture page plus registry plus expected verdict run through `runChecks` against the real bundle row, so the fixture proves the comparator semantics the row states (no registry entry files Missing Info; the approved attachment in the slot passes even with launch words on the page; another attachment is a mismatch naming the observed asset).

**What the playbook must assert (this repository).**

- `tests/build-checks.mjs` refuses a row whose comparator is not in `spec/observer-comparators.json` or whose `observerCheck` is not in `registry/observer-checks.json`, and refuses a registry name with neither a row nor a retirement.
- `tests/observer-conformance.test.mjs` (in `npm test`) asserts the bundle carries the comparator copy verbatim and every row uses it, every row and retirement names a registered check, the registry names appear in one family each, every `pendingInObserver` name has a row, and the conformance row has the shape above.
- `tests/sync-observer-comparators.mjs` (`npm run sync:observer`) refetches the observer's `spec/supported-comparators.json` from `superbuilders/aeo` main (GitHub token from `--token`, `GH_TOKEN`, `GITHUB_TOKEN` or `gh auth token`) and reports drift (exit 1); `--write` rewrites the copy so the next build sees the observer's list; `--checks` also refetches `src/checks.mjs`, re-extracts the check ids the way `--observer-source` does, and names the ids the observer emits that the registry lacks (each needs a row or a retirement) and the registry names it no longer emits. Run it whenever the observer changes; a new comparator lands in the observer first, then here, then in a row.
