# What the observer must do to use the field map

The production observer (`superbuilders/aeo alpha-site-system`) today compares the site with sources and reports "site says A, source says B". To file tickets that a fresh agent can execute, it needs the pathway logic from `spec/campus-page-field-map.json`. Required changes, in order:

1. **Read HubSpot Programs directly.** Set `HUBSPOT_PROGRAMS_ENDPOINT` (it has no default today, so every campus-fact check is inert) with a token that has `crm.objects.custom.read` and `crm.schemas.custom.read`, and add `website_campus_intro`, `cognia_accredited`, `admission_link`, `form_program_interest_label`, `wordpress_post_id`, and `visibility` to the property list. The growth map API stays the fallback for state and mirrored facts.
2. **Add the status-sentence check.** For every Open Program: the page's `content_body_4` first sentence must equal "<name> is open and enrolling."; for Announced: a month or season plus a year. Compare both the page and `website_campus_intro` against the rule. Emit `expectedSource: HubSpot Programs type`, `actualSource: website_campus_intro` when the text contradicts the state.
3. **Classify by pathway before dispatch.** For each failing check, resolve the element in the field map and emit the defect class (data, mapping, delivery, presentation) and the ticket class. Route `hubspot-data` to the hubspot-program-admin, `sync-mapping` and `sync-delivery` to the n8n-sync-owner, event classes to the events-plugin-owner and hubspot-owner, and only presentation classes to the website operators. Today every campus rule routes to `#support-websites` with Matt and Yash as owners.
4. **File with the template.** The APEX ticket body carries the element, CSS ID, source system and field, source value with read time, expected value and rule, class, owner, fix path, and done condition (protocol step 1b templates). `tests/diagnose-field.mjs` is the reference implementation; the observer can call it or port it.
5. **Know the run schedule.** Treat a page modified at 00:15 to 01:00 Central as rewritten by n8n. A mismatch after that window with a correct source is `sync-delivery`, not a website defect. Replace the unexplained 2-hour grace constant for events with the plugin's 30-minute interval plus one cycle.
6. **Check synced elements exist.** Port `n8n-synced-elements-present` from `tests/page-check.mjs` so a layout change that drops a CSS ID is caught before the nightly run fails.

Until 1 to 4 land, the loop's campus-fact and launch-copy findings are triaged by an agent running `tests/diagnose-field.mjs` before any ticket is worked.

## Added 2026-09-17: event permalinks redirect by design

- `event-page-reachable` and the HTTP checks on `alpha.school/events/<slug>/` must follow redirects and judge the final response. Every event permalink on alpha.school answers 301 or 302 to its `events.alpha.school/register/<uuid>/` page, and the Upcoming Events listing links there directly. Three tickets (Palo Alto open house 522, Miami Beach coffee 404, San Francisco open house 502) were transient or a re-slugged event; all three resolve to a 200 registration page today and were set For Review.
- A 404 on an event permalink whose HubSpot event was re-synced under a new slug (`-2`) is a plugin behavior, not a content defect; the old slug 301s. The check should treat a 301 to the same event's new slug as pass.
- Render-timeout findings (page.goto 20 s) need a second attempt before a ticket is filed. Five tickets from the September 14 run were filed for pages that answer in 0.3 to 3.6 s today.

## Added 2026-09-24: the check bundle is the definition

- The observer loads `spec/check-bundle.generated.json` (built by `tests/build-checks.mjs` from `spec/check-rows.json`; hash in `spec/release-manifest.json` `checkBundleSha256`) and cites the row `id` and bundle `version` on every finding. Thresholds, host lists, exemptions, grace periods and source contracts are rows there; the observer's config keeps only credentials, schedules and rendering budgets. Rows with `channel: loop-health` go to the observer owner and suppress the rows they name; rows with `status: advisory` are measured, never filed; a check in `retired[]` stops running.
- Item 5 above is superseded for events: the row `site.events.sync.public` sets the grace to four hours after an event becomes public (the published-inventory read lagged the plugin import by one to four hours in the 2026-09-24 sweep), and every event row carries `suppressWhen: event-ended`.
- Grades (item 1): compare `start_grade_level` and `end_grade_level` only (`campus.facts.grades`); `grade_levels` is an orphaned property HubSpot no longer defines and `grades_served` is never read.
- Brand leak: read `registry/sister-brand-exceptions.json` for both the word list (`brands[]`) and the exceptions; the config list is retired.
- Render timeouts: `site.header.rendered.route-reachable`, `campus.page.reachable.program-page`, `site.events.sync.page-reachable` and `site.events.sync.registration-reachable` carry `requireConsecutiveRuns: 2`.
- Every current check name is in `registry/observer-checks.json`; refresh it with `node tests/build-checks.mjs --observer-source <aeo>/alpha-site-system/src/checks.mjs` when a check is added or removed.

## Added 2026-09-25: promotion rule, depth, source digest, filer trigger (check bundle 1.2)

- **Promotion rule.** A row is enforced only when its `grounding` names a complaint, a source contract, an exemplar or a decision (the 2026-09-15 precedence, in that order of authority: decision, source-of-truth system, exemplar, complaint). A row whose grounding is `none` is built as `status: advisory` with `advisoryReason` set, whatever `spec/check-rows.json` declares: the observer measures it and reports it, the filer never files it. Promoting a row means grounding it (a decisions.md row, a spec or registry contract, an exemplar URL, or the ticket or findings document that complained) and rebuilding; nobody edits `status` on an ungrounded row.
- **Depth.** Every row carries `depth: render | http` (`spec/README.md`, "Depth contract"). Render campus pages, the homepage, Locations and the events pages (and the `map-routes` and `critical-routes` groups) in the browser on both viewports; fetch every other route over HTTP once; read `map-source` rows from the sources with no fetch. Never take a rendered measurement on an `http` row; the builder refuses such a row and a finding that claims one is telemetry.
- **Source digest.** Rows with `channel: source-digest` (the `map-source` comparisons between the Operations sheet, the growth map API and HubSpot Programs, and the Community record, URL form and host rows) are emitted like any other finding, with `expectedSource`, `actualSource` and `sourceReadAt` filled, because the filer turns each into an audit line for the owner role in `source-digest.md`; they never become website tickets and the observer never dispatches them anywhere itself.
- **Filer trigger.** When `site-observe.yml` completes with conclusion success, send `repository_dispatch` `observer-run-completed` to `trilogy-group/alpha-website-playbook` with `client_payload.run_id` (this GitHub run id), `client_payload.mode` (`full` or `events`) and `client_payload.conclusion`; the playbook's filer workflow is a receiver for that event (cross-repository `workflow_run` is not supported) and files after each full run, with a fallback cron at 06:45 and 21:45 UTC. The token needs `repo` dispatch rights on the playbook repository. Until the dispatch step lands in aeo, the fallback cron carries the cadence.
- **Cadence.** Full render runs at 06:00 and 21:00 UTC; events lane every two hours; source contracts daily at 06:30 UTC; loop-health rows every run. `clearAfterRuns: 2` means two consecutive full runs, about one day.
